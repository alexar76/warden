# Что WARDEN нашёл в 1 108 публичных MCP-серверах — и в чём ошибся

> 🌐 [English](mcp-survey.md) · **Русский** · [Español](mcp-survey.es.md) · [Français](mcp-survey.fr.md) · [中文](mcp-survey.zh.md)

24 августа 2026 года, через несколько часов после публикации `@aimarket/warden` 0.3.0, мы направили
его на все публичные MCP-серверы, до которых имели право дотянуться: 2 787 серверов из
официального реестра с сетевым эндпоинтом, из них 1 108 ответили на настоящий `tools/list` и отдали
17 491 определение инструмента.

Главный результат — не про экосистему. Он про нас. WARDEN заблокировал 50 из 1 108 серверов, и
только в **4** случаях из 50 мы смогли подтвердить реальную проблему. Остальные 46 — это ошибки
нашего сканера, шести видов, каждый из которых мы можем назвать, воспроизвести и исправить.

Мы публикуем провалы вместе с доказательствами, потому что профиль ложных срабатываний — единственное
число, которое решает, включит ли сканер хоть кто-нибудь. Сканер поисков отравленных инструментов,
который отказывает честным серверам, — это не осторожный сканер, а сканер, который удаляют. Ruleset
v1 уже научил нас этому один раз.

## Что именно измерялось

| | |
|---|---|
| Тестируемый пакет | `@aimarket/warden@0.3.0`, установленный из реестра npm в пустой проект — не рабочая копия |
| Действующий ruleset | v2, `sha256-gWC14PR4kUylkJaAGMnIYYX6tPhZTJ60cSB61UZxuWc=` (см. [дефект релиза](#дефект-релиза) ниже) |
| Корпус | `registry.modelcontextprotocol.io`, 8 000 записей → 3 121 уникальный сервер → 2 787 с удалённым эндпоинтом |
| Способ получения | MCP `initialize` + `tools/list` по streamable-http, одна попытка на сервер, таймаут 20 с |
| Задействованные гейты | `static-scan` и `threat-feed` (встроенный deny-list, без удалённого фида) |
| Не задействованные | `origin` и `pinning` — оба решают по *состоянию хоста* (объявлял ли оператор этот сервер, изменились ли определения с момента одобрения), ни один не является свойством сервера, и в обзоре оба вернули бы один и тот же ответ для всех 1 108 |
| Политика | `blockAtSeverity: "high"`, `allowUnknownServers: true`, `pinToolDefs: false` |

**Чужой код не запускался.** Каждое определение инструмента получено из ответа самого сервера по
сети. Именно поэтому корпус — удалённые серверы, а не stdio-серверы из разнообразных awesome-списков:
дотянуться до тех означает скачать и запустить чужой код, а обзор по безопасности такого себе
позволять не должен.

### Достижимость — сама по себе находка

Рукопожатие завершили лишь 41% заявленных в реестре удалённых эндпоинтов:

| Исход | Серверов |
|---|---|
| ответили на `tools/list` | 1 149 (41,2%) |
| отказ с 4xx (нужна авторизация либо больше не существует) | 1 215 |
| ошибка соединения / TLS | 298 |
| транспорт `sse`, не пробовали | 37 |
| 5xx | 34 |
| несовпадение протокола (нет пригодного результата `initialize`) | 21 |
| редирект / 410 / 429 | 32 |

Из 1 149 ответивших 1 108 заявили хотя бы один инструмент. Тому, кто пишет клиент к реестру, стоит
рассчитывать логику повторов и авторизации на **59% отказов при первом контакте**.

## Что подтвердилось

Четыре сервера действительно заявляют инструменты, через контекст модели у которых проходит
секретный материал. Мы описываем их, не называя: они не ведут себя злонамеренно, они делают
законную работу так, что хост агента и правда должен ставить на этом гейт, а обзор — не место для
раскрытия уязвимостей.

- Сервер казны для рынка предсказаний, чей инструмент принимает `signer_private_key` с описанием
  *«signer EOA private key, 0x…»*. Подписывающий ключ кошелька, запрошенный как параметр API. Ровно
  тот случай, для которого WARDEN и существует.
- Сервер платежей между агентами, который выделяет sandbox-кошелёк и *«return[s] its private key
  exactly once»* через канал инструмента.
- Сервер идентичности агентов, чья проза инструмента велит модели прочитать локальный
  `credentials.json` и записать `private_key` в виде JWK на диск с `chmod 0600`.
- Управляемая СУБД с параметром `pvkPassword` — *«Password that encrypts the private key»*.
  Документированный параметр крупного облачного API — и всё-таки секрет в схеме инструмента.

Это 4 из 50 заблокированных, или 4 из 1 108 просканированных. Всё дальше — про остальные 46.

## Что не подтвердилось

### 1. Слепота к полярности — крупнейший дефект

`TOOL_DEF_SECRET_REQUEST` ищет словосочетание `private key`. Он не читает окружающее предложение.
Поэтому всё нижеперечисленное заблокировано с уровнем `critical`. При пороге по умолчанию соединение
отклоняют и `high`, и `critical` — то есть сервер целиком, все его инструменты, — а `critical` вдобавок
обнуляет счёт гейта:

> Never send a private key: none is needed and the request is refused if one is present.
> — генератор DANE/TLSA-записей

> Use this to import your own public key so you can SSH into instances. **The private key never
> leaves your machine.**
> — менеджер облачных инстансов

> YOU sign and broadcast the returned transaction yourself, with your own wallet's private key, on
> your own infrastructure — **Otto never sees or holds your key**.
> — сервер котировок обмена

> …does NOT confirm the certificate matches any private key.
> — инспектор сертификатов

> Use exact field names from this schema; **do not guess aliases or include private key material.**
> — SAP-сервер, в шаблоне схемы **всех своих 377 инструментов**

Последний пример — вся суть проблемы в одной строке: сервер, который велит модели *не* присылать
приватные ключи, оценивается так же, как тот, который их просит; а поскольку правило `critical`, одно
совпадение существительного в общем шаблоне отклонило сервер и обнулило его счёт. 390 из наших 492 блокирующих срабатываний — это одно это существительное.

`TOOL_DEF_SECRET_HARVEST` — глагол из списка `read|extract|retrieve|fetch|obtain|dump|reveal|collect|…`
в пределах 30 символов от существительного-секрета — ломается так же:

> Anyone holding the URL can read it, so **never store secrets**, credentials or personal data
> — сервер временного хранения

> Public read-only: **never collect card data, secrets or email**
> — сервер бронирования

> it does **not** reveal or mint a standalone agent credential
> — сервер регистрации агентов

Три сервера заблокированы за письменное обещание не делать того, что ищет правило.

### 2. Слепота к роли — блокируются сами сканеры

Определение инструмента, которое *описывает* атаку, оценивается так, будто оно её *совершает*. Пять
серверов, все — защитные инструменты:

> …for prompt-injection and social-engineering (`'ignore previous instructions'`, `'send funds to'`,
> `'approve this'`, `'admin override'`, `'claim your airdrop'`…)
> — проверщик инструкций, заблокирован по `ignore previous`

> hidden directives that hijack agents — instruction overrides, `'don't tell the user'`, data
> exfiltration, secret harvesting, tool-shadowing, and invisible-unicode / homoglyph steganography
> — сканер MCP-эндпоинтов, заблокирован по `exfiltration`

> `"enum": ["exfiltration", "recon_then_destroy", "injection_then_action"]`
> — конструктор политик, заблокирован по значениям собственного enum

> Detect likely leaked API keys, tokens, private-key headers, JWTs…
> — сканер секретов, заблокирован по `private-key`

Атакующий напишет отравленный инструмент, не называя атаку. Защитник называет её в каждом
предложении. Наши правила отбирают защитника.

### 3. «do not tell the user» — это инструкция на честность

Правило `TOOL_DEF_INJECTION` трактует `do not tell the user` как сокрытие. Во всех реальных
случаях, что мы нашли, — четыре сервера, четыре из четырёх — всё наоборот: сервер не даёт модели
сообщить пользователю *неправду*.

> some convert in real time during the session, others batch once or twice daily, so **do NOT tell
> the user** a payment is "held until the next session"

> AFTER payment succeeds, no refund is issued automatically — the result says so explicitly; **do
> not tell the user** a refund is coming

> a `facturx-en16931` result is the payload and not a Factur-X document — **do not tell the user
> otherwise**

> **Do not tell the user** to drag assets into chat

На реальных данных предпосылка правила перевёрнута. Добросовестные авторы серверов используют эту
фразу, чтобы подавить выдуманные успокоительные заверения, — то есть именно то поведение, которого
хост агента и хочет.

### 4. Столкновения лексики

- **`system prompt`** → `TOOL_DEF_INJECTION`, 15 срабатываний на 6 серверах. Все шесть — прокси к
  LLM, менеджеры персон или инструменты настройки агентов, чья единственная задача — задать system
  prompt, и которые объявляют параметр `system` в схеме. Это слово здесь предметная область, а не
  атака.
- **`\bjavascript:`** с флагом `i` → `TOOL_DEF_DATA_URL`, high. Оно совпадает со словом *JavaScript*
  и следующим двоеточием, а именно так пишется любой список языков на свете:
  *«TypeScript/JavaScript: `*.spec/test.{ts,js}`»*, *«plain async JavaScript: …»*,
  *«javascript: Enable JavaScript execution»*. И срабатывает на серверах, которые сообщают, что эту
  схему вырезают: *«the sanitizer strips … `javascript:` and `data:text/html` URIs»*.
- **`data:…;base64,`** → то же правило, на image-API, у которых пример в схеме буквально
  `"<url> OR data:image/png;base64,..."`, и на скрапере, который пишет, что *отфильтровывает* схему
  `data:`.
- **окно в 30 символов** у `SECRET_HARVEST` перескакивает границы предложений и JSON:
  `read an open or sealed run (pass api_key` — совпадение, тянущееся из прозы в имя параметра.

### 5. Слепота к кодировке — WARDEN отмечает систему письма

`TOOL_DEF_HIDDEN_UNICODE` сообщает о «zero-width or bidi control characters hiding text from
review». Один сервер задел его пять раз. Это иранский сервер юридических расчётов, а символ —
**U+200C ZERO WIDTH NON-JOINER**, *обязательный* орфографический знак персидского языка:

- `بخشنامه‌ها` (циркуляры)
- `سهم‌الارث` (наследственная доля)
- `حق‌الثبت` (пошлина за регистрацию)
- `حق‌التحریر` (нотариальный сбор)

Ничего не спрятано. Так пишется этот язык. В нынешнем виде правило наказывает серверы на
персидском, арабском и индийских письменностях за их орфографию — контроль безопасности,
читающийся как языковая политика, а это хуже ложного срабатывания.

У `TOOL_DEF_BASE64_BLOB` зеркальная ошибка: `/` входит в алфавит base64, поэтому глубоко вложенный
указатель JSON Schema — `#/properties/flow/items/anyOf/2/properties/outcomes/items` — попадает в
отчёт как «a long base64-encoded blob — possible hidden payload».

### 6. Wildcard'ы threat-фида совпадают с подстроками

Встроенный deny-list использует wildcard'ы вида `*a*b*` против склеенного определения инструмента,
без границ слов и без ограничения на расстояние:

- `*sweep*funds*` совпал с инструментом выкупа floor'а ENS: *«Floor-sweep: buy the CHEAPEST N listed
  ENS names»* … *«and **refunds** the excess»*. Шаблон нашёл `funds` внутри слова **refunds**.
- `*drain*wallet*` совпал со сканером против drainer'ов: *«Find risky allowances that could
  **drain** your tokens»* … *«a **wallet** granted»*. Инструмент существует, чтобы останавливать
  drainer'ов.
- `*seed*phrase*` совпал с инструментом подбора ключевых слов для YouTube: *«For a **seed** topic,
  returns suggested search **phrases**»*.

Все три отмечены как `critical` с сообщением *«Crypto-drainer keyword in server identity»* — которое
вдобавок неверно указывает, *где* совпало: это определение инструмента, а не идентичность сервера.

## Что сработало точно как задумано

Единственная часть ruleset'а, которая выдержала контакт без потерь, — **разделение на уровни**.
Срабатывания `advisory` случились 3 472 раза — `TOOL_DEF_CREDENTIAL_PARAM` 2 016,
`TOOL_DEF_IMPERATIVE` 1 437, `TOOL_DEF_ENV_REFERENCE` 19 — и не заблокировали ничего, не снизили ни
одного балла и не изолировали ни одного инструмента. При ruleset v1, где `api_key` в схеме был
блокирующим, эти 2 016 срабатываний отказали бы значительной части честной экосистемы. Урок v1→v2 на
реальных данных подтверждается; работа осталась в правилах блокирующего уровня.

## Дефект релиза

Пакет, которым мы сканировали, сообщает ruleset **v2**, digest `sha256-gWC14PR4…`. README **внутри
того же архива** описывает ruleset **v3** и печатает digest `sha256-pah/sT4I…`. Оба утверждения
верны — про разный код:

| | |
|---|---|
| `0.3.0` опубликован в npm | 2026-08-24 08:34:08 UTC |
| коммит, вынесший пакет | 2026-08-24 08:35:12 UTC — через 64 секунды |
| коммит, добавивший ruleset v3 | 2026-08-24 09:26:50 UTC — через 52 минуты после публикации |

То есть у артефакта, который ставит посторонний человек, нет ни одного правила на поверхности
`name`, где v3 держит 17 из своих 24 правил; символ нулевой ширины или base64-блоб в *имени*
инструмента для него невидим.

Затем мы измерили, чего это стоит. Мы прогнали тот же корпус на сборке v3 и сравнили по серверам,
инструментам и кодам:

**Разницы нет.** 444 сервера со срабатываниями, 50 заблокированных, 3 964 срабатывания — идентично
на обоих ruleset'ах. Ни один из 1 108 настоящих серверов не кладёт в имя инструмента ничего, что
поймает v3 и пропустит v2. Устаревшая публикация — реальный дефект процесса, защита от него в CI стоит пунктом 9 ниже; на
этом корпусе её влияние на поведение нулевое, и мы предпочитаем это сказать, чем намекать на
серьёзность, которую не измеряли.

## Что изменилось по итогам

Всё это вышло как ruleset **v4** в `@aimarket/warden` 0.4.0, digest
`sha256-klRyTiD3njdBs7sOjcDCfmAHaKsfQi75/wlQjjWWkXI=`. У правил появились именованные **guard'ы** —
проверки контекста, решающие, действительно ли совпадение — то, что правило ищет. Guard входит в
публикуемую таблицу правил и потому в digest: одно и то же регулярное выражение с `polarity` и без —
это разные сканеры, и записанный вердикт должен уметь сказать, какой из них работал.

| Guard | Что решает |
|---|---|
| `polarity` | Существительное-секрет внутри отрицания — это обещание, а не запрос; проверяется и клауза вокруг, и сам совпавший фрагмент |
| `mention` | Фраза в кавычках, в бэктиках или как значение JSON `enum` — цитата, а не высказывание |
| `detection` | Секрет как объект `detect` / `scan` / `find` / `leaked` — это то, что сканер ищет |
| `identifierFragment` | `mnemonic` внутри `bip39-mnemonic-checksum` — часть имени этого идентификатора |
| `harvestTarget` | Инструкция на сбор говорит, *чей* секрет или *где* он лежит |
| `uri` | `javascript:` теперь регистрозависим и требует payload после себя |
| `payload` | `data:…;base64,` с менее чем 32 символами после запятой документирует формат |
| `blob` | Порог энтропии и ключевые слова схемы, чтобы указатель `$ref` не читался как скрытая нагрузка |
| `zeroWidth` | U+200C/U+200D рядом с арабским, персидским или индийским письмом — это орфография |
| `publicKeyPath` | `authorized_keys`, `known_hosts` и `*.pub` публичны по определению |

Четыре блокирующих правила понижены до advisory — каждое, как показали измерения, отбирало честные
серверы: голое существительное `exfiltrat*`, `system prompt` / `developer message`,
`do not tell the user` и — только по уровню, с `critical` на `high` — существительные-секреты, чтобы
одно слово в общем шаблоне схемы больше не читалось как «сервер максимально скомпрометирован».

У threat-фида появился свой матчер: внутренние разрывы wildcard'ов ограничены 24 символами, а
сегмент, начинающийся с буквы, должен начинаться на границе слова. `_` и `-` считаются границами,
поэтому поле схемы `seed_phrase` по-прежнему ловится, а `funds` внутри «refunds» — нет. У
`policy.sensitiveToolPatterns` семантика обычного glob сохранена: там оператор писал свой паттерн под
свои же имена инструментов.

Сообщения о находках теперь цитируют совпавший текст. Раньше они обрезали шаблон до
`signature (\b(?:read|extract|…)`, и проверяющий не мог понять, какая альтернатива сработала и на
чём. Восстановление этого вручную и составило большую часть работы над этим обзором.

### Повторное измерение на тех же 1 108 серверах

| | ruleset v3 (как в обзоре) | ruleset v4 |
|---|---|---|
| серверов заблокировано | 50 | **6** |
| из них подтверждённых | 4 | **4** |
| блокирующих срабатываний | 492 | 9 |
| advisory-срабатываний | 3 472 | 3 494 |
| серверов хоть с одним срабатыванием | 444 | 439 |

Все четыре настоящие находки по-прежнему блокируются — регрессионный набор проверяет оба
направления, и он построен на реальном тексте этого корпуса, а не на выдуманных фикстурах: никто,
садясь придумывать тестовые данные, не напишет «the private key never leaves your machine» и не
наберёт описание с персидским ZERO WIDTH NON-JOINER.

### Что всё ещё срабатывает и почему мы это оставили

Два из шести оставшихся блоков — по-прежнему наши:

- Инструмент блокчейн-форензики `wallet_funds`, на встроенном паттерне `*drain*wallet*`. В его
  описании стоит *«did they drain the project wallet»* — эти два слова действительно рядом, так что
  ограничение на расстояние тут не поможет. Это слепота к роли на уровне threat-фида, а у фида нет
  понятия «защитник». Дать подписанным threat-записям механизм guard'ов — большее изменение модели
  доверия фида, чем стоит делать в этом проходе.
- `get_ssh_command` у облачного хостинга, на `~/.ssh` внутри документированного вызова
  `ssh -i ~/.ssh/<keypair_name>`. Определение инструмента, указывающее модели на каталог SSH-ключей
  пользователя, пожалуй, стоит отметки; блокировки — пожалуй, нет. Оставлено как есть, а не
  подогнано под один пример.

### Гейт релиза

`npm run check:ruleset` падает, если версия из `package.json` уже лежит в реестре с другим ruleset
ref. Он работает в CI и в `prepublishOnly`, и при первом же запуске поймал живой дефект, описанный
выше: 0.3.0 опубликован как v2, исходники на v4. Теперь смена правил требует смены версии.

## Ограничения

- **Один транспорт.** Только streamable-http; 37 `sse`-серверов пропущены, а все stdio-серверы
  экосистемы вне охвата из-за правила «не запускать чужой код». При этом stdio-серверы — большинство
  того, что люди реально запускают локально.
- **Один момент времени.** По одному `tools/list` на сервер, 24 августа 2026 года. Определения
  инструментов меняются, и сервер, честный на момент запроса, может позже подменить описание — как
  раз для этого существует гейт `pinning`, и именно pinning этот обзор проверить не мог.
- **«Ложное срабатывание» — наша оценка.** Мы прочитали определение инструмента и решили, что метка
  неверна. Мы не проводили аудит серверов, и ложное срабатывание на *определении* не удостоверяет
  *реализацию*: инструмент с безупречной прозой всё ещё может сливать данные при вызове.
  Статический разбор определений этого не видит по построению.
- **Нет эталонной разметки.** В корпусе ничего не размечено. Мы можем сообщить, что 46 из 50
  блокировок были неверны; мы не можем сообщить, сколько отравленных серверов прошли мимо нас.
  Ложноотрицательные для этого метода невидимы, и цифра точности 4/50 ничего не говорит о полноте.
- **Серверы за авторизацией отсутствуют.** 1 215 серверов отказали без учётных данных. Это
  непропорционально часто коммерческие серверы, поэтому корпус смещён в сторону открытых и
  любительских.

## Как воспроизвести

Здесь не нужна наша инфраструктура и никакие ключи. Скрипты — в
[`scripts/mcp-survey/`](../scripts/mcp-survey/), агрегат — в
[`data/mcp-survey-2026-08-24.json`](data/mcp-survey-2026-08-24.json).

```bash
cd scripts/mcp-survey
python3 harvest_registry.py          # реестр -> registry_remotes.json
python3 harvest_tools.py             # живой tools/list -> tools_raw.jsonl
npm install @aimarket/warden@0.3.0
node scan.mjs tools_raw.jsonl scan.json
python3 classify.py                  # точный совпавший фрагмент на каждое блокирующее срабатывание
```

`harvest_tools.py` делает два-три запроса на сервер и ничего не запускает. При повторном прогоне
ваши числа достижимости будут отличаться от наших — эндпоинты появляются и исчезают в течение часов.
