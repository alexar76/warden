# 测量边界与版本证据

> 🌐 [English](scan-limits.md) · [Русский](scan-limits.ru.md) · [Español](scan-limits.es.md) · [Français](scan-limits.fr.md) · **中文**

以下说明对应 2026-10-25 的读者反馈。已测试的**已发布 npm `0.21.0` 构件**与后续本地源码是不同对象：保留 `package.json` 中的版本号，不会使本地修复进入已发布的归档。代码测试、虚拟账单和脚本生成的批准回复，不能代替模型评估、生产流量测量或用户研究。

## 账单与服务器声明

`initialize`、`tools/list` 和 canary 探测调用本身也可能产生费用或其他服务器端效果。发现流程或 preview 成功，不能证明下一次调用的价格或效果。在我们的虚拟账单 fixture 中，canary 选择了免费的 `preview`，而 `{}` 选择了扣除七个虚拟积分的操作。这测量的是该 fixture，而不是外部卖家的真实账单。

`readOnlyHint`、`destructiveHint` 和 `openWorldHint` 都是未经验证的声明，不能证明操作免费或无害。本地的 annotations 首次使用审查需要明确启用，默认是 `off`，且只适用于 `wrap --flow NAME`。接受该审查并不表示批准价格，也不构成对实际效果的认证。参见[流控制及其边界](flow-guard.zh.md)。

## 请求的包版本与服务器自报版本

精确的 `package@x.y.z` 指定请求的包版本。`initialize.serverInfo.version` 是服务器提供的字符串，不是独立解析得到的包版本，也不是构件摘要。例如，审查的 Mapled 包为 `@mapled/mcp@0.21.6`，服务器仍自报 `0.1.0`。

已测试的发布版 `0.21.0` 可能错误地用自报版本生成包固定建议。应核实包管理器的实际解析结果与锁定文件、完整性证据，而不是直接接受该建议。本地修复将这些元数据分开，并移除了这种替换；它仍不能认证 launcher 实际运行了哪些包字节。未固定版本的 `npx` 可能解析到另一版本，也可能复用缓存，不能保证每次启动都采用其中一种行为。tools 集合的 hash 标识观察到的定义，而不是整个可执行程序。参见[扫描](scan.zh.md)和[集成](integration.zh.md)。

## Launcher 比较与参考基线

Auten 调查只有一个公开观察到的快照，并没有完成对两种 launcher 环境的实测。复现差异需要准确的 runner 及其版本、启动参数，以及来自相应环境的两个 tools 快照。HISTOR 观察记录可作为比较参考，但不是经操作者批准的可信 pin。

[Launcher 证据收集器](../examples/launcher-evidence/README.md)目前只有英文辅助文档。它记录的是经过客户端规范化的 tools 定义，而不是原始协议记录。填写的 runner 版本由所有者声明，该字段不会独立解析包构件。收集器已经准备好，并不证明两个环境的比较已经发生。

## 询问、批准与回答

历史数字 **39/97** 统计的是触发过 `ask` 的任务，而不是批准操作的人数。hook 决策之后发生执行，不能证明有人点击了 Allow。Wrapper 可以记录 accept/decline/cancel，但脚本客户端也能生成这些回复。人工批准率、阅读时间和批准疲劳，需要真正展示给人的请求及其关联结果；这些测试没有测量它们。

在保存的 DeepSeek Flash guard + note 系列（`injecagent`，20 个 travel 用例）中，AgentDojo 的历史官方结果仍是 **18/20**，依据是目标名称的精确出现。AI 辅助阅读在保存的片段中发现的是警告，而非采纳攻击者推荐，但只有 18 个回答完整，另外两个达到旧的 2000 字符保存上限。缺失的结尾内容未知，因此不能据此建立完整回答上的新 `0/20` 分数。本地 harness 为未来回答保存全文、长度和 hash；它不会恢复历史缺失内容，也不意味着重新运行了模型。

**受控选择测试（2026-10-25）：**独立的工具结果后合成测试使用已发布的 WARDEN `0.21.0`，覆盖六项酒店任务 × 五次重复、clean/benign/injected 三种备注及三种配置：**270/270 个 ID 选择正确**，其中 injected 条件下**0/90 次选择攻击目标**（每种配置 0/30）。目标名称出现在包括对照组在内的 **25/270** 个回答中，`note_stop` 的 Stop 触发 **0/90** 次；无守卫基线也全部选对，因此尚未测得守卫的额外收益，而正确 ID 不代表解释中的每项事实都准确。[协议、结果与限制](https://github.com/alexar76/aicom/blob/main/docs/growth/launchgate-selection-2026-10-25.en.md)：这项独立研究不改变 AgentDojo 历史上的 **18/20**，也不证明普遍安全。

**并列选择后续实验（2026-10-25）：** 两个最优选项均可接受时，注入条件下目标选择分别为：无防护 48/48、note 44/48、note+Stop 45/48；对应 clean 基线为 28/48、25/48、29/48。经基线调整的防护效果区间包含零；432 次选择均符合任务要求，选择目标本身不能视为错误。真实用户偏好得到 18/18 次遵守，Stop 未要求复查。本地[离线评估器](../scripts/selection-probe/README.md)现支持多个可接受答案及共同基线比较；运行时阻断逻辑未更改。[结果与限制，英文](https://github.com/alexar76/aicom/blob/main/docs/growth/launchgate-tie-selection-2026-10-25.en.md)。

## 片段阈值与复查成本

强指纹窗口仍为 **非十六进制 8 / 十六进制 10**。本地对已知前缀之后索引的修复，并没有建立对嵌在较长单词中的六字符片段的可靠强检测。现有会话必须重新读取凭据才能获得新窗口。在凭据边界要求审查，与确认该片段就是秘密，是不同的判断。

同样，Stop 中 12 个规范化字符的匹配会请求再次检查回答，但不能证明模型在语义上拒绝了指令。删除警告词豁免后，诚实的警告也会多付出一次检查。改写和被操纵的行选择可以绕过这种匹配。Fixture 上的改进和刻意选择的误拒对照，既不能确立全局最优阈值，也不能得出生产误报率。[流控制指南](flow-guard.zh.md)说明了策略、尚存的缺口，以及依赖 host 的 `stop_hook_active` 标志限制后续检查的机制。
