# Подписанный threat feed

> 🌐 [English](threat-feed.md) · **Русский** · [Español](threat-feed.es.md) · [Français](threat-feed.fr.md) · [中文](threat-feed.zh.md)

WARDEN поставляется с 11 встроенными записями об угрозах. Это минимум, а не каталог: смысл feed в том,
чтобы тот, кто действительно охотится на враждебные MCP-серверы, мог доставить свои находки в каждую
установку — и при этом не получил возможности что-либо *разблокировать*.

## Контракт на проводе

```
GET https://ваш-хост/threat-feed

{
  "records": [
    { "pattern": "*wallet-drainer*", "severity": "critical", "code": "THREAT_CRYPTO_DRAINER",
      "reason": "Crypto-drainer keyword in server identity", "source": "your-scanner",
      "scope": "server" }
  ],
  "timestamp": 1786205907380,
  "signature": "f588d5a4…9706"
}
```

| Поле | Правило |
|---|---|
| `records` | массив `ThreatRecord`; записи, не прошедшие проверку типа, отбрасываются, но это не фатально |
| `timestamp` | epoch **в миллисекундах, целое**. Не опционально — именно оно делает replay обнаружимым |
| `signature` | Ed25519, hex, по канонической форме RFC 8785 от `{records, timestamp}` — **не** по сырому телу ответа |

`ThreatRecord`:

| Поле | Смысл |
|---|---|
| `pattern` | сопоставляется без учёта регистра; `*` — glob, паттерн без `*` — обычная проверка на подстроку |
| `severity` | от `info` до `critical`. `critical`, совпавший с **сервером**, фатален для соединения |
| `code` | стабильный машинный код, например `THREAT_TYPOSQUAT` |
| `reason` | человеческая формулировка, показываемая оператору |
| `source` | кто это утверждает — переносится в находку |
| `scope` | `server` \| `tool` \| `any` (по умолчанию). На какой поверхности паттерн осмыслен |

Scope важнее, чем кажется. `*token*` — разумный паттерн для *идентичности сервера* и катастрофический
паттерн для *инструмента*: половина честных MCP-серверов упоминает токены в схеме.

## Что WARDEN проверяет и что делает при отказе

Правило для всех отказов ниже одно и то же: **сохранить встроенный минимум**. Feed, который не удалось
проверить, игнорируется; он никогда не понижает уже имеющуюся защиту и никогда не блокирует запуск.

| Проверка | Какой сценарий она останавливает |
|---|---|
| `feedPublicKey` настроен | Неподписанный feed отвергается сразу — нет ключа, нет удалённых записей, даже если URL задан |
| Подпись Ed25519 по каноническим байтам | Тот, кто раздаёт URL, не может добавить или изменить записи |
| Свежесть: подписанный `timestamp` в пределах `maxAgeMs` (по умолчанию 24 ч, `DEFAULT_FEED_MAX_AGE_MS`) | Реплей снимка месячной давности, молча стирающий все добавленные с тех пор записи. *Подпись говорит, кто написал документ, но никогда — когда его вам вручили* |
| Сдвиг в будущее: не более чем на `FEED_CLOCK_SKEW_MS` (5 минут) вперёд | Timestamp далеко в будущем, который вечно держал бы устаревший документ «свежим» |
| Канонические байты (RFC 8785) | Расхождение издателя и проверяющего из-за порядка ключей в JSON |
| Размер: `content-length` и тело ≤ 512 000 байт | Использование URL feed как вектора исчерпания памяти; тело проверяется тоже, потому что content-length может отсутствовать или лгать |
| Таймаут запроса 10 с | Подвисший feed, блокирующий ваш запуск |

Удалённые записи **добавляются к** встроенным (`[...BUILTIN, ...remote]`). Feed не может удалить
встроенную запись, а значит скомпрометированный издатель не может выключить защиту — только дополнить
её. Эта асимметрия намеренная: канал наверх (любой сообщает о подозрении) и канал вниз (feed, который
может запретить сервер) не должны иметь один уровень доверия.

## Как публиковать feed, который WARDEN примет

Ключ генерируется один раз. WARDEN ожидает публичный ключ в виде **hex-кодированного SPKI DER** (88
hex-символов для Ed25519):

```js
import { generateKeyPairSync } from "node:crypto";

const { publicKey, privateKey } = generateKeyPairSync("ed25519");
const spkiHex = publicKey.export({ format: "der", type: "spki" }).toString("hex");
console.log(spkiHex); // → это и есть то, что потребители закрепляют как feedPublicKey
```

Подписывайте каноническую форму `{records, timestamp}` — используйте канонизатор самого WARDEN, чтобы
реализация байтов была одна, а не две:

```js
import { sign } from "node:crypto";
import { canonicalize } from "@aimarket/warden/jcs";

function document(records, privateKey) {
  const timestamp = Date.now();                       // целое, мс
  const payload = canonicalize({ records, timestamp }); // порядок ключей задаёт RFC 8785
  const signature = sign(null, Buffer.from(payload, "utf8"), privateKey).toString("hex");
  return { records, timestamp, signature };
}
```

Две вещи, на которых спотыкаются издатели:

- **Не кешируйте документ.** `timestamp` — это заявление о свежести; закешированный ответ рано или
  поздно опубликует устаревший, и каждый потребитель его отвергнет.
- **Подписывайте каноническую форму, а не `JSON.stringify`.** Они совпадают гораздо чаще, чем
  расходятся, — именно поэтому расхождение потом так дорого искать.

## Как потреблять

```ts
const feed = new ThreatFeed({
  feedPublicKey: process.env.FEED_PUBKEY,   // закреплён заранее, вне канала
  maxAgeMs: 6 * 60 * 60 * 1000,             // опционально; не-конечное/≤0 откатывается на 24 ч
  log: myLogger,                            // опционально, но именно сюда пишутся отказы
});
await feed.load(process.env.FEED_URL);      // без URL → только встроенные, без сети
```

`feed.builtins` возвращает встроенный минимум, если нужно показать, что действует вообще без feed.
Каждый отказ — это `log.warn` с причиной: без логгера молча пустой feed и отвергнутый feed
неразличимы, поэтому в продакшене логгер передавайте.

## Референсный издатель

[MOMUS](https://github.com/alexar76/momus) публикует этот контракт по `/warden/threat-feed`, отдаёт
SPKI-ключ в hex и счётчики записей через `/warden/threat-feed/summary`, а также принимает
непроверенные подозрения с полей через `/warden/report`. Его проверочный скрипт
(`momus/scripts/verify_warden_channel.mjs`) проверяет живое развёртывание канонизатором **этого
пакета** — единственный способ доказать, что обе стороны согласны насчёт байтов.
